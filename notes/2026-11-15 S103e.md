'gfam:g-robin-1203' does not run on the junk queue — but I'm in the
assessed queue!" - the S103d walk's FIRST live 403.

advertised on the junk bar TOO (api rode status in ('assessed','junk')
from the S103b cut) while the gfam route's scopes are ASSESSED ONLY
(the trainer reviews live rows; a junk run is a refusal). A lozenge
clicked on junk 403s; the FLASH LINGERS ACROSS the in-place doorway

failure after navigating to /q/assessed. My reproduction walk went:
junk bar carries the lozenges (live check) -> the click path posts
queue=junk -> the route's honest 403 -> the flash rides the hop.

THE FIX (both ends):
1. THE ADVERTISEMENT MATCHES THE ROUTE'S OWN SCOPES: family_plugins
   ride the ASSESSED payload only (junk's bar carries NO family
   lozenges — verified live: junk [], assessed [both]).
2. THE STALE-FLASH CLEAR: flashMsg stamps filtermsg.dataset.qid (the
   message binds the queue that raised it); render() calls
   renderFlash() per render — a flash whose qid != the current QID
   clears (display none). Verified: the simulated 403 flash visible

THE WORKING RULE RE-EARNED: (a) AN ADVERTISED GATE MUST MATCH THE
ROUTE'S GATE: a lozenge rendered where the route refuses is a
broken affordance — the advertisement is a COPY of the scopes, not
a generous superset (the same law as S097's widget scoping). (b) A
FLASH IS A QUEUED MESSAGE WITH AN OWNER: persistent-status slots
must bind their owning context and clear on hop (the trap class
this session already visited as stale-bar, S082d).
