## S039    2026-10-26    picods101 outage triage and SD-card forensics

**Incident**: the user reported both camera nodes unavailable in the morning; imagebank (<bank-ip>) remained up. Network probes later showed **picods100 (<node-ip-2>) was healthy**: `/` on port 8080 returned HTTP 200, and `stats.json` reported `started=09:05:36`, `frames=2212` at 10:20. **picods101 (<bank-ip-2>) was unavailable**: no ping, ARP entry, mDNS response, or HTTP response on port 8080. This narrowed the incident to picods101; it did not establish whether the cause was storage, power, Wi-Fi, or hardware.

**SD access workflow and findings**:
- Windows mounted only the card's FAT32 `bootfs` partition as `D:` (~512 MiB). The MBR showed partition 2 as type `0x83`, starting at byte 545,259,520 and sized 125,126,574,080 bytes (~116.5 GiB); Windows did not mount this ext4 rootfs.
- The available Ubuntu-22.04 WSL2 instance is `aarch64`; its `/dev` contained only WSL virtual disks, not the physical SD-card reader. `drvfs` access to `D:` exposes the boot partition only. Don't assume WSL can directly mount a card inserted in the Windows reader.
- A non-elevated PowerShell raw open of `\\.\PhysicalDrive1` was denied. An elevated PowerShell launched via UAC could read it. The ext4 superblock was found at partition-2 offset +1024; magic `0xEF53` at superblock offset `0x38`, state field `1`, mount count `5`, max mount count `-1`, and volume label `rootfs` were visible. This confirms an ext4 superblock and no superblock error flag; it is **not** a filesystem check and does not rule out damage elsewhere.
- Boot `cmdline.txt` contains `fsck.repair=yes`; this is normal repair-on-boot configuration, **not evidence that fsck caused the outage**. The boot partition's `config.txt` was stock; its cloud-init seed files were dated 2026-10-24.
- The user elected to reflash the SD card and rebuild picods101 rather than continue imaging. **No full image was made; no writes, filesystem repair, or other changes were made to the card during inspection.** The rootfs logs/journal were not recovered, so the cause remains undetermined.

**Future SD-card forensic procedure**: before reimaging a failed node, label and preserve its card; get a sector-by-sector image of the whole physical card (or at least partition 2) using an elevated, verified imaging tool, save it to a different disk, verify the image, and perform `e2fsck -fn`/read-only mounting against the image  "not the original card. WSL raw-device passthrough must be confirmed explicitly; this machine's WSL2 setup did not provide it. Capture the final console/LED state and node/power details before teardown. Avoid diagnosing filesystem corruption from a steady LED alone.

**Maintenance follow-up**: treat Pi/SD longevity as a separate maintenance topic. Review SD write amplification and endurance, root/log rotation and persistent write volume, power supply/cable quality and undervoltage evidence, storage free-space/health checks, periodic verified backups/images, and a recovery/rebuild runbook. Prefer writing camera frames to the existing RAM-backed storage and NAS paths; don't add frequent health writes to the SD card.
